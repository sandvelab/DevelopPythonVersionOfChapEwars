### JC-01

- **Call**: Which data is development and which is the sealed holdout
- **Choice**: Dev: EWARS monthly example + Nicaragua weekly before 2018; holdout: Laos monthly subset + Nicaragua weekly from 2018
- **Alternatives considered**: (a) The plan's default, holdout = one or two whole chap-core datasets with weekly development on the EWARS `example_data/`. Rejected: that weekly example has 8 periods, too short for a lagged backtest, so the weekly code path would first meet real data at the holdout. (b) A location split of the Nicaragua data. Rejected: chap backtests forecast every location jointly, and the iid spatial effect is fitted per location, so a location holdout tests a different thing from a time holdout. (c) Monthly holdout from `small_laos_data_with_polygons3.csv`. Rejected: its periods are weekly ranges, so it is not monthly.
- **Basis**: Chosen from file names, columns, row counts, location ids (no overlap with the monthly development locations) and period ranges only, before any values were looked at. The 2018 cut leaves 14 years of weekly history for development and about 5 years of held-out targets.
- **Agency**: agent-autonomous; information: agent-retrieved
- **Where recorded**: AI-internal/data-acquisition/partition_data.py; plan §4b 2026-10-14
- **Does it move the conclusion?** not yet tested (phase D)
- **Settled**: 2026-10-14, batch 1

### JC-04

- **Call**: Which future-weather provider chap's backtest uses
- **Choice**: `climatology`, chap's default, passed explicitly: the covariates of each forecast window are forecast per location from month/week of year, not taken from the observations
- **Alternatives considered**: `observed` (chap's legacy provider): the model sees the true future rainfall and temperature, which isolates the model from weather-forecast error. Not chosen: chap names climatology as the setting that reflects production, it is what chap does unless told otherwise, and R and Python see the identical covariates either way, so the fidelity comparison does not depend on the choice. A candidate perturbation for phase D.
- **Basis**: chap_core/assessment/weather_providers/__init__.py (DEFAULT_WEATHER_PROVIDER_ID = 'climatology'); api_types.BacktestParams description.

### JC-05

- **Call**: What the model is given from the development files
- **Choice**: Each file reduced to the six-column chap data contract (time_period, rainfall, mean_temperature, disease_cases, population, location); rows and values copied exactly
- **Alternatives considered**: (a) The archived files as they are. Fails for monthly data (CH-07). (b) Drop only `month`. Rejected: the other derived columns (ID_year, E, Cases) are also used by predict.R when present and are also forecast by chap's weather provider for the future window, so they would reach the model altered too; dropping all of them is the same rule for every dataset. (c) Switch the weather provider to `observed` so the columns survive. Rejected: it changes the backtest, not the input (JC-04).
- **Basis**: The EWARS README's data contract lists the six columns, and says the derived columns are produced by predict.R's adapters, so 'callers do not need to supply them'. Diagnosis in results/diagnose_monthly/ shows the reduced monthly file runs.
